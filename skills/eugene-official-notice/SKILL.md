# 업무연락 문서 생성 (eugene-official-notice)

유진그룹 사내 "업무연락" 공문 양식을 그대로 재현해 `.docx` 파일을 생성한다.
서식(로고·글꼴·여백·들여쓰기·줄간격·서명)은 스크립트에 하드코딩되어 있으니 건드리지 않는다.
**이 스킬의 실제 일은 서식이 아니라 내용 구성이다** — 사용자에게 키워드·메모만 받아,
사람이 쓴 것처럼 적절한 위치와 위계로 배치된 완결된 공문을 만들어내는 것.

생성 스크립트: `scripts/generate_memo.py` (python-docx 필요 — 없으면 `pip3 install python-docx`)
로고 이미지: `assets/logo.jpg`

## 흐름

1. **최소 정보만 받기**: 완성된 문장을 요구하지 않는다. 키워드·메모·구어체 몇 줄이면
   충분하다고 안내하고, 있는 만큼만 받는다 (전부 없어도 진행 가능).
   발신/수신 · 제목 · 날짜(생략 시 오늘) · 요지 · 항목 · 첨부/연락처/표 · 비고/서명란.

2. **구성 판단**: 아래 "## 구성 원칙"에 따라 각 내용을 어디에 어떤 위계로 놓을지 정한다.
   **받은 순서대로 정해진 슬롯에 욱여넣지 않는다.**

3. **JSON 스펙 작성**: "## JSON 스키마"에 맞춰 스크래치패드에 작성한다.

4. **생성 실행**:
   ```bash
   python3 .agents/skills/eugene-official-notice/scripts/generate_memo.py <spec.json> <output.docx>
   ```
   출력 파일명 규칙 — 사용자의 현재 작업 디렉토리에 저장한다:
   ```
   업무연락-{발신팀}-{업무연락개요}-{YYYYMMDD}.docx
   ```
   - **{발신팀}**: 우선은 `"AI_CoE"`로 고정한다 (sender에서 자동 추출하지 않음).
   - **{업무연락개요}**: `title`을 핵심 키워드 중심으로 축약.
   - **{YYYYMMDD}**: `date`("2026. 08. 12") → `20260812`.
   - 세그먼트 사이는 하이픈(`-`), 세그먼트 내부 띄어쓰기는 밑줄(`_`).
     예: `업무연락-AI_CoE-계열사_AI_추진_현황_조사_및_자료_제출_요청-20260812.docx`

5. **눈으로 검산**: `qlmanage -t -s 1200 -o <dir> <file>` 로 썸네일 PNG를 만들어 Read
   도구로 **직접 열어보고** "## 검산 체크리스트"를 확인한다. 걸리는 게 있으면 고쳐서
   다시 생성한다. 이 단계를 건너뛰지 않는다 — 대부분의 문제는 렌더링을 봐야 보인다.

6. **보고**: 파일 경로와 함께, 사용자가 준 그대로가 아니라 **이번에 새로 완성하거나
   기본값으로 채우거나 덜어낸 부분**만 bullet 2~4개로 알린다. 그대로 옮긴 부분은
   나열하지 않는다. 발송 전에 사용자가 틀린 데만 골라 고칠 수 있게 하는 것이 목적이다.

## 구성 원칙

### A. 무엇을 어디에 놓을지 (구조)

- **블록 종류를 먼저 고른다** (`sections`의 `type`):

  | 내용 성격 | 블록 |
  |---|---|
  | 절차·조건을 순서대로 짚음 | `numbered` — "1. 조사 대상 : ~" |
  | 한 주제 아래 여러 항목을 묶어 나열 (개요, 요청 사항, 참고 사항, 문의처) | `heading` — 굵은 소제목 + 대시 불릿 |
  | 비교표·일정표처럼 행/열로 구조화된 데이터 | `table` |
  | 첨부파일 | `attachments` |

  항목이 5개를 넘거나 성격이 다른 그룹(배경/요청/참고)이 섞이면, 번호 하나로 뭉치지 말고
  `heading`으로 나누는 쪽이 사람이 쓴 것처럼 읽힌다.

- **도입부(`intro`)는 "- 아 래 -" 위쪽 전체가 2~3줄**. 담는 것은 ① 왜 이 일을 하는지
  ② 그래서 무엇을 요청하는지, 딱 둘이다. 대상·양식·제출 방법 같은 **구체적 조건·절차는
  아래 항목에 있으므로 도입부에서 뺀다.** `intro`가 문단 리스트를 받긴 하지만 기본은
  한 문단이고, 나눠서 4줄을 넘으면 합치거나 줄인다.

- **도입부 첫 문장은 상대의 현 상태를 문제로 진단하지 않는다.** 그 문장을 읽는 사람이
  대개 그 상태를 만든 당사자라, 진단은 지적으로 읽힌다. 같은 필요를 누구의 잘못도 아닌
  **상황 변화**로 쓴다.
  - 나쁨: "자료가 각 사·개인별로 흩어져 있어 다시 확인하는 데 시간이 소요되고 있습니다"
  - 좋음: "AI 과제 추진이 본격화되면서 회의록과 검토 자료가 꾸준히 쌓이고 있습니다"

- **※ 표시는 예외·단서에만 쓴다.** 판단 기준은 "본문에서 말한 원칙에 대한 예외나
  단서인가"이지 **"덜 중요한가"가 아니다.** 활용 계획·추진 배경·시행 방식 같은 설명은
  그냥 본문이므로 번호 항목으로 쓴다. 인사말은 더더욱 ※가 아니다(→ `outro`).
  - 좋은 ※: "투자심의 대상금액에 충족하지 않더라도 사전협의가 가능" (원칙의 예외)
  - 나쁜 ※: "이번 조사 결과는 ~ 기초자료로 활용할 예정입니다" (그냥 본문 → 번호 항목)

- **`emphasis: true`(▶ 굵게)는 회신처가 발신자와 다를 때만 쓴다.** 다른 부서·다른 담당자
  에게 보내야 해서 잘못 보내기 쉬운 경우가 그 자리다. 발신 부서가 그대로 받는 경우
  (공문을 보낸 메일에 회신하면 되는 경우)에는 ▶를 쓰지 않고 일반 "- " 항목으로 적는다 —
  안 그러면 그 한 줄만 문서에서 떠 보인다.

- **부분 볼드는 `**...**`로 감싼다** (intro·outro·notes·item text 어디서나 동작).
  **읽는 사람이 놓치면 곤란한 값**에만 쓴다 — 회신 기한, 지정 인원 수, 금액, 시행일.
  문서당 2~3곳을 넘기지 않는다. 강조가 늘면 아무것도 강조되지 않고, 문장 전체를 굵게
  하면 어조가 위압적으로 바뀐다. 항목 제목("1. 담당자 지정")은 이미 위계로 구분되므로
  굵게 하지 않는다.

- **위계는 최대 2단계** (section → item → aside). 괄호 번호 (1)(2)(3)를 겹쳐 쓰거나
  불릿 기호를 뒤섞지 않는다. 작업 디렉토리에 그런 예시 문서가 있어도 모범이 아니라
  **어수선해지기 쉽다는 반례**로 본다.

- 첨부는 `sections` 어디에 적어도 스크립트가 맨 끝(비고·맺음말 뒤, 서명 직전)에
  자동 배치하므로 위치는 신경 쓰지 않는다. 표기는 "붙임. ~ 1부." 또는 "별첨 1. ~".

### B. 어떻게 쓸지 (문장)

- **어투는 사용자가 쓴 결을 따른다.** 합니다체로 줬으면 합니다체로 쓴다. 기준 원본의
  "~함/~가능" 개조식으로 기계 변환하지 않는다 (실제 업무연락에 두 문체 모두 쓰인다).
  단, 번호 항목의 라벨성 문구("조사 대상 : 그룹 전 계열사")는 어느 문체에서든 간결하게.

- **요청 문장은 상대가 할 행동을 동사로 쓴다.** "협조하여 주시기 바랍니다"는 받는 사람이
  뭘 해야 하는지가 없는 상투어다 → "작성하여 제출하여 주시기 바랍니다", "회신하여 주시기
  바랍니다", "담당자를 지정하여 통보하여 주시기 바랍니다".

- **요구만 늘어놓지 않되, 예의는 기능하는 것만.** "왜 이걸 하는지"(→`intro`)와 맺음
  인사 한 문장(→`outro`)은 있어야 통보문처럼 읽히지 않는다. 사용자가 준 배경 설명이나
  인사를 "공문체로 압축한다"며 잘라내지 않는다. 반대로 "감사합니다", "바쁘신 와중에"
  같은 정보 없는 상투어는 넣지 않는다.

- **새 도구·절차 도입처럼 상대에게 없던 부담을 지우는 요청이면, 요청 항목만 쓰지 않는다.**
  받는 쪽에서 "왜 이걸 굳이"가 나오는 문서다. 세 가지를 항목으로 넣어 균형을 맞춘다 —
  ① 운영 목적(상대에게 돌아가는 이득으로 쓴다: "담당자 변경 시에도 맥락이 이어짐",
  "건별 자료 요청·취합을 최소화함". 발신 부서의 편의로 쓰지 않는다), ② 발신 부서의 지원
  사항(우리가 대신 하는 일을 명시해 상대의 할 일을 좁힌다 — 단 **확정된 절차만** 쓴다.
  "양식·안내를 제공하겠다"처럼 아직 준비되지 않은 약속은 지어내지 않는다), ③ ※ 예외 경로
  ("내부 정책상 어려운 경우 연락 주시면 대안을 협의"). 강한 어미를 부드럽게 고치는 것보다
  이 세 가지가 있는 편이 훨씬 덜 강압적으로 읽힌다.
  단, 비용 부담 주체처럼 메일·구두로 따로 안내되는 사항은 사용자가 넣으라고 하기 전에는
  공문에 쓰지 않는다.

- **항목 제목은 한 줄에서 끝낸다.** 두 줄로 넘어가면 "라벨: 내용" 구조가 무너진 것이니,
  라벨만 남기고 내용을 하위 불릿으로 내리거나("조사 항목" + 불릿 5개) 문장을 줄인다.

- **본문의 클론(:)은 앞말에 붙이고 뒤만 띄운다** — `조사 대상: 그룹 전 계열사` (O),
  `조사 대상 : 그룹 전 계열사` (X). JSON에 " : "로 써도 스크립트가 자동으로 고쳐주지만
  (`15:00`, 이메일, `https://`처럼 앞뒤 공백이 없는 클론은 건드리지 않는다) 처음부터
  맞게 쓴다. **머리말도 예외가 아니다** — `발신: ` / `수신: ` / `참조: ` / `제목: `으로
  쓴다(스크립트가 이 형태로 생성한다). 라벨 글자 사이를 벌리던 `발 신 : `은 옛 관행일
  뿐 맞춤법에 어긋나므로 되돌리지 않는다.

### C. 무엇을 덜어낼지 (감산)

가장 자주 놓치는 부분이다. 사용자가 준 원문에는 같은 취지가 여러 번 나오는 게 보통이고
(도입 인사와 맺음말에 목적이 두 번), 그대로 옮기면 문서가 늘어진다.

- **한 정보는 한 자리에만.** 도입부 / 항목 / ※ 비고 / 수신란은 역할이 다르다 —
  도입부는 "왜 보내는가", 항목은 "무엇을 어떻게 하라는가", 비고는 "예외·단서",
  수신란은 "누구에게". 같은 말이 두 군데 있으면 덜 적합한 쪽을 덜어낸다.
  - 도입부 문구가 아래 항목과 같은 말을 하면 → 도입부에서 뺀다 (아래에서 어차피 말한다).
  - 수신이 "각 사 AI CoE 연락담당자"인데 항목에 또 "각 사 AI CoE 연락담당자가 ~ 제출" → 뺀다.

- **알맹이 없는 항목은 만들지 말고 지운다.** 기한·제출처·금액처럼 항목을 항목답게 만드는
  정보가 없어서 도입부에 이미 있는 말만 되풀이하게 된다면 그건 껍데기다. 억지로 채우지
  말고 빼되, **"기한/제출처를 주시면 항목으로 넣겠다"고 사용자에게 짧게 알린다.**

- **사실은 지어내지 않는다.** 날짜·금액·부서명·수치·정책명처럼 그 자체가 사실인 항목은
  사용자가 주지 않으면 만들지 않는다. 합리적인 기본값이 있으면(시행일 = 문서 날짜) 쓰고,
  그조차 애매하면 짧게 되묻는다. 반면 문맥상 뜻이 분명한 절차성 문장은 채워도 된다.

## 검산 체크리스트

썸네일을 열어 다음을 확인한다. (괄호는 위반 시 참고할 원칙)

- [ ] "- 아 래 -" 위쪽이 2~3줄 이내인가? (A)
- [ ] 도입부 / 항목 / 비고 / 수신란을 나란히 읽어 같은 말이 두 번 나오지 않는가? (C)
- [ ] ※로 붙인 것이 정말 예외·단서인가? 그냥 설명이면 번호 항목으로. (A)
- [ ] 요청 문장에 상대가 할 행동이 동사로 들어 있는가? (B)
- [ ] 번호 항목 제목이 두 줄로 넘어가지 않는가? (B)
- [ ] 내용 없이 자리만 차지하는 항목이 없는가? (C)
- [ ] 레이아웃이 깨지지 않았는가(페이지 넘침 등)?

## JSON 스키마

스키마 전체 설명과 예시는 `scripts/generate_memo.py` 상단 docstring에도 있다.

```json
{
  "date": "2026. 04. 20",
  "sender": "그룹혁신부문 비전추진본부",
  "recipient": "각 사 기획부서장",
  "cc": "각 사 전략 담당 임원",
  "title": "...",
  "intro": "배경·목적과 요청 취지 (2~3줄)",
  "sections": [
    {"type": "numbered", "text": "적용 대상 : ...",
     "items": [{"text": "...", "aside": "※로 붙는 예외·단서(선택)"}]},

    {"type": "heading", "heading": "요청 사항",
     "items": [
       {"text": "..."},
       {"text": "담당자 연락처: ...", "emphasis": true}
     ]},

    {"type": "table", "headers": ["구분", "A", "B"], "rows": [["학습 목표", "...", "..."]]},

    {"type": "attachments", "items": ["붙임. ~ 1부."]}
  ],
  "notes": ["문서 전체에 걸린 예외·단서(선택)"],
  "outro": "각 사의 적극적인 협조를 부탁드립니다.",
  "ending": "signature",
  "closing": "그룹혁신부문 비전추진본부"
}
```

- `sections`는 순서대로 렌더링되는 블록 리스트. `numbered`만 자동 번호가 매겨지고
  `heading`/`table`/`attachments`는 번호를 소비하지 않으므로 자유롭게 섞을 수 있다.
- `intro`/`outro`는 문자열 하나 또는 문단 리스트. `outro`는 ※ 없이 본문 문단으로
  들어가는 맺음 인사 자리다.
- `items[].emphasis: true` → "- " 대신 "▶ " 굵게. `items[].aside` → 같은 불릿 안에서
  줄바꿈 후 "※ ..." 부기. 문서 전체 비고는 top-level `notes`.
- `attachments`는 어디 적어도 본문 맨 끝에 자동 배치된다.
- `cc` 생략 시 "참 조" 줄이 안 나온다.
- `ending`: `"signature"`(기본, 발신 부서명 굵게 중앙) 또는 `"kkeut"`(서명 없이 마지막
  줄 끝에 "끝." — 문의처로 끝나는 안내문에 적합). `"kkeut"`이면 `closing` 무시.
- `closing` 생략 시 `sender`와 동일.

## 서식 관련 (건드릴 일 없음)

- 로고·글꼴(맑은 고딕)·여백·줄간격·들여쓰기는 원본과 동일하게 하드코딩되어 있다.
  사용자가 서식 자체를 바꿔달라고 하지 않는 한 스크립트를 수정하지 않는다.
- 긴 문장은 강제 개행 없이 통짜로 넣고 Word 자동 줄바꿈에 맡긴다. 직접 줄바꿈 위치를
  계산해 끊으면 폰트 메트릭 오차로 줄 끝이 부자연스럽게 잘린다. 한글 문서에서 단어
  중간이 줄 끝에서 잘리는 것은 정상이다.
- 모든 계층("1. ", "- ", "▶ ", "※ ", "붙임. ")에 걸림 들여쓰기가 걸려 있어 줄이
  넘어가도 이어지는 줄이 텍스트 시작선에 정렬된다. 섹션 사이 여백도 자동이다.
  들여쓰기가 어색하면 JSON이 아니라 스크립트 상수(`ITEM_INDENT_T`, `SUB_INDENT_T`,
  `*_HANGING_T`)를 본다.
- 문서 속성(작성자·수정 시각·생성 프로그램)도 일반 Word 문서처럼 자동으로 채워진다.
- 여러 건을 연달아 요청받으면 매번 새 JSON과 새 출력 파일로 독립 생성한다.

## 이 스킬을 계속 다듬기

사용자가 결과물을 보고 피드백을 주면(어투가 어색하다, 들여쓰기가 이상하다, 이건 왜 여기
있냐 등), 그 문서만 고치고 끝내지 말고 **원인을 이 파일이나 스크립트에 반영한다.**
- 내용 판단 문제(무엇을 어디에 놓을지, 어떤 문장을 쓸지) → "## 구성 원칙"에 반영하고,
  재발을 막을 수 있으면 "## 검산 체크리스트"에도 한 줄 추가.
- 렌더링·레이아웃 문제(들여쓰기, 여백, 위치) → `scripts/generate_memo.py` 수정.
  JSON 내용으로 우회하지 않는다.
반영할 때는 지난 규칙과 충돌하지 않는지 보고, 겹치면 합친다 — 규칙이 쌓이기만 하면
적용하기 어려워진다.
