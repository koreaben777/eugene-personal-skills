# 유진그룹 프로젝트 다음 할 일

## 목적

흩어진 현황을 한 번에 모아 **이 사용자가 이 프로젝트에서 지금 무엇을 해야 하는지** 알려 준다. 결과물은 대화 답변 하나다.

조사는 전부 읽기 전용으로 한다. Notion 업무 갱신, 커밋, push, PR, 메시지 발송은 할 일로 제안만 한다. 실제 실행은 사용자가 따로 지시할 때 한다.

## 적용 범위와 경계

- **대상 범위**: `~/Documents/Eugene_Group` 아래 프로젝트만 대상이다.
  - 작업 경로가 그 밖이면 Eugene 규칙이 적용되지 않는다. 이 스킬의 대상이 아니라고 알리고 멈춘다.
  - Eugene_Group 루트에서 시작했으면 어느 프로젝트인지 묻는다. 선택지는 `AGENTS.md`가 있는 하위 폴더로 만든다.
- **지침 읽기**: 시작 전에 루트 `AGENTS.md`, `유진_AI_CoE_Notion_사용가이드.md`, 그리고 작업 경로까지 있는 모든 프로젝트 `AGENTS.md`를 읽는다. 규칙이 겹치면 더 엄격한 쪽을 따른다. 같은 세션에서 이미 읽었다면 다시 읽지 않는다.
- **Finder `보안` 태그**: 프로젝트 지침이 태그 판정을 요구하면(예: 한일합섬) 파일 내용을 열기 전에 그 절차대로 판정한다. 판정에 실패하면 그 파일은 열지 않는다.
- **Notion**: 검색, 페이지 조회, 스키마 조회, 데이터 조회만 한다. data source ID는 추측하지 않는다. 데이터베이스를 먼저 가져와 그 안에 적힌 ID를 쓴다. Notion 도구가 없거나 호출이 실패하면 로컬 근거만으로 진행하고, 빠진 출처를 보고에 적는다.
- **Git**: 저장소마다 원격 소유자를 먼저 확인한다.
  - `eugene-aicoe/*`이면 `eugene-team-git-rules` 스킬을 먼저 실행한다.
  - 개인 저장소이면 루트 `AGENTS.md`의 개인 저장소 규칙을 따른다.
  - 어느 경우든 원격 참조를 갱신하는 fetch·pull은 하지 않는다.
- **사용자 신원**: 기존 로컬 신원 파일은 필요한 범위에서 읽기만 한다. 신원을 클라우드 메모리나 Notion, 공유 문서에 적지 않는다. 신원·역할 메모리 생성/갱신은 사용자가 명시적으로 요청하고 프로젝트 지침이 허용할 때만 한다. 한일합섬의 장기 기억 생성 금지를 우선한다.
- **실행 금지**: ERP·업무 DB 접속, 서버 실행, 외부 모델 호출은 하지 않는다. DB에서 실제 값을 확인해야 풀리는 항목은 할 일로만 남긴다.
- **런타임 차이**: Claude에서는 AskUserQuestion, Codex에서는 사용 가능한 사용자 입력 도구를 쓴다. 도구가 없으면 같은 선택지를 대화로 묻는다. 선택적 질문에 답이 없으면 현재 개요서로 추천을 진행하되 개요서 수정은 하지 않는다. 필요한 신원 확인이나 변경 승인은 답 없이 진행하지 않는다.

### Codex에서 사용

- 이 스킬은 Eugene_Group의 `.agents/skills/eugene-next-tasks/`에 있으며 한일합섬의 같은 경로에서도 연결된다. `$eugene-next-tasks` 또는 "내 다음 할 일 추천해줘"로 사용한다.
- Notion은 현재 연결된 Codex 도구를 검색하고 `fetch(self)`로 권한을 확인한 뒤 읽기 전용으로 조회한다. Claude/goose의 인증·설정을 복사하거나 해당 CLI·외부 모델을 실행하지 않는다. 내부 파일 내용·추출 결과를 검색어 또는 도구 인자로 외부 전송하지 않는다.
- 병렬 수집은 독립적인 도구 호출에 한정한다. 하위 에이전트는 현재 요청이나 적용 지침이 명시적으로 허용할 때만 사용한다.
- 기존 `~/.claude/eugene-local-user.md`는 읽기 전용 신원 근거로 재사용할 수 있다. Codex 메모리나 별도 신원 파일로 복사하지 않는다. 기존 메모리에서 얻은 주장은 현행 근거와 대조하고, 해당 런타임의 메모리 인용 규칙을 따른다.
- 날짜·요일·기한은 사용자 시간대(이 프로젝트는 Asia/Seoul)를 기준으로 한다.

## 절차

### 0. 개요서 갱신 여부 묻기

개요서가 낡았으면 그 위에 세운 할 일도 낡는다. 그렇다고 갱신이 공짜는 아니다. 다른 대화와 Notion을 전부 훑어야 해서 시간이 오래 걸린다. 그래서 진행 전에 사용자에게 묻는다.

1. 프로젝트 루트에서 `*개요서*.md`를 찾는다. 이름에 `.bak`이 들어간 백업 파일은 제외한다. 개요서가 없으면 이 단계를 건너뛰고, 보고의 확인 경계에 "개요서 없음"을 적는다.
2. 개요서는 파일이 클 수 있으므로 전체를 읽지 않는다. 첫 `작성일` 줄(`grep -m1 '작성일'`)과 파일 수정 시각만 확인한다.
3. 쓸 갱신 스킬을 정한다. 프로젝트 `.agents/skills/project-outline-update/`가 있으면 그것을 쓴다(프로젝트 스킬이 전역 동명 스킬보다 우선한다). 없으면 전역 `project-outline-update`를 쓴다.
4. 해당 런타임의 사용자 입력 도구로 묻는다. 질문에는 작성일과 오늘 날짜를 함께 보여 준다.
   - `바로 진행`: 현재 개요서를 기준으로 하되, 작성일 이후 바뀐 것은 2단계에서 직접 확인한다.
   - `개요서 먼저 갱신`: 갱신 스킬을 끝까지 실행한 뒤 1단계로 돌아온다.
   - 작성일이 오늘이면 `바로 진행`을, 그렇지 않으면 `개요서 먼저 갱신`을 추천 선택지로 첫 자리에 둔다. 추천 이유는 한 줄로 적는다.
5. 사용자가 요청에서 이미 정했다면 묻지 않는다(예: "개요서는 건너뛰고").
6. 개요서를 갱신했다면, 갱신 중에 이미 조회한 Notion·저장소 결과를 2단계에서 다시 조회하지 않고 그대로 쓴다.

### 1. 사용자와 역할 확인

1. **이름**: `~/.claude/eugene-local-user.md`를 읽는다.
   - 파일이 없으면 현재 프로젝트의 자동 메모리에서 신원 노트를 찾는다.
   - 그래도 없으면 이름을 묻고 멈춘다. 이름을 추측하지 않는다.
   - 확인한 이름은 이번 답변에서만 사용한다. 이 추천 요청만으로 신원 파일을 만들거나 고치지 않는다.
2. **역할**: Notion에서 이 프로젝트의 최신 역할 기록을 찾는다.
   - 검색어는 "<프로젝트명> 역할 분담", "<프로젝트명> 업무 분담"이다. 보통 회의록에 정·부 표로 있다.
   - 프로젝트 레지스트리 항목의 담당자 속성도 참고한다.
   - 역할은 "추후 변경 가능"으로 잠정 배정되는 경우가 많으므로, 로컬 메모리보다 최신 기록을 우선한다.
3. **기존 역할 메모 대조**: 기존 역할 노트가 최신 기록과 다르면 차이를 답변에 적는다. 이 추천 요청만으로 메모리를 생성하거나 갱신하지 않는다.
4. **역할 기록이 없을 때**: "역할 기록 없음"이라고 적고, 사용자에게 배정된 업무만 기준으로 진행한다.
5. **필터 정리**: 역할 범위를 한 줄로 정리한다. 무엇을 정담당으로 맡는지, 어떤 부담당과 짝인지 적는다. 이 정리가 3단계의 필터가 된다.

### 2. 현황 수집 (읽기 전용, 서로 독립이면 병렬)

| 출처 | 가져올 것 |
| --- | --- |
| 개요서 | `grep -n '^#'`로 목차를 본 뒤 필요한 범위만 읽는다: 결론 절의 최신 문단, 가장 최근 날짜의 현황 절, 역할과 관련된 쟁점, 권장 다음 단계 |
| 프로젝트 문서 | 개요서보다 새로 바뀐 파일(`find . -newer <개요서> -type f`, 산출물·캐시 폴더 제외)과, 가장 최근의 회의 준비·질문 목록 문서 |
| Notion 공용 DB | 가이드의 공용 DB를 쓴다. 프로젝트 레지스트리에서 이 프로젝트 항목을 찾는다. 업무 진행상황에서는 담당자가 사용자이거나 이 프로젝트에 연결된 미완료 항목을 본다. 회의록은 최근 2주, 일정 캘린더는 오늘부터 2주를 본다. 회의록에서는 액션 아이템에 사용자 이름이 있는지 확인한다 |
| Notion 프로젝트 전용 페이지 | "<프로젝트명> 대시보드"처럼 프로젝트 전용 업무 카드·이슈·로드맵 DB가 있으면 전부 조회한다. 공용 DB와 겹치면 `최근 수정`이 늦은 쪽을 현행으로 본다 |
| Git 저장소 | 프로젝트 안의 저장소(`find . -maxdepth 3 -name .git`)마다 다음을 본다: `git status -sb`, `git branch -vv`(원격에 없는 로컬 브랜치 확인), 통합 브랜치와 기본 브랜치의 차이(브랜치 이름은 규약에서 확인), 최근 커밋 몇 개. 원격 최신 여부가 판단을 바꾸면 `git ls-remote --heads <remote>`로 참조를 갱신하지 않고 대조한다 |
| 자동 메모리 | `MEMORY.md` 색인에서 진행 중 작업 노트(남은 항목, 미병합, 승인 대기 등)를 골라 읽는다. 메모리에 적힌 주장은 저장소나 파일과 대조한 뒤에 쓴다 |

### 3. 대조하고 추리기

이 단계가 스킬의 핵심이다. 업무 목록을 그대로 옮기지 않는다. 기록을 실제 상태와 맞춰 본다.

- **기록과 실제가 어긋나는 경우**: 업무·카드 상태를 저장소와 문서 사실에 맞춰 본다. 예를 들어 `할 일`인데 이미 병합됐거나 산출물이 있으면 "기록 갱신" 항목으로 올린다. 기록의 최근 수정이 오래됐으면 그렇다고 적는다.
- **지속 업무**: 개발이 이어지는 동안 계속 반복되는 업무가 있다(예: 개발한 코드를 팀 저장소에 올리기). 이런 카드는 이번 분량이 끝났어도 완료 처리를 제안하지 않고, 상태와 현황 문구만 갱신하도록 제안한다. 지속 업무인지 애매하면 완료를 제안하기 전에 사용자에게 묻는다. 프로젝트 메모리에 지속 업무로 적힌 카드는 묻지 않는다.
- **역할 범위 필터**: 사용자에게 배정된 업무뿐 아니라 역할 범위에 속하는 부담당·타인 업무, 받는 사람이 사용자인 이슈도 포함한다. 이런 항목은 "같이 볼 것"으로 표시한다.
- **외부 일정 역산**: 고객 미팅, 방문, 보고, 마일스톤이 가까우면(D-1 이내) 그 준비물을 가장 앞에 둔다.
- **팀 운영 규칙**: 정기 갱신 요일 같은 규칙이 Notion이나 지침에 있고 오늘이 해당되면 할 일에 넣는다.
- **막힘 구분**: 지금 바로 할 수 있는 일과 현업 자료·답변·승인을 기다리는 일을 나눈다. 기다리는 일에는 무엇을 기다리는지 적는다.
- **현업 질문 분류**: 질문은 답할 부서별로 나눈다. 프로젝트 메모리에 질문 범위 규칙이 있으면 따른다.
- **구현 수행 주체**: 현행 프로젝트 지침을 따른다. 한일합섬은 Codex가 직접 수행하며 종료된 Claude → goose 위임을 다음 업무로 제안하지 않는다.
- **승인 게이트**: PR 병합이나 외부 발송처럼 승인이 필요한 일은 누가 승인하는지 적는다.

### 4. 보고

아래 형식을 쓴다. 각 항목은 **무엇을 → 왜/근거 → 완료 조건** 순서로 짧게 적는다. 우선순위와 기한이 있으면 붙인다. 해당하는 항목이 없는 절은 뺀다.

업무·카드를 가리킬 때는 번호만 쓰지 않는다. `HS-4 프로토타입 신규 기능`처럼 번호와 제목을 같이 적는다. 제목이 길면 앞부분만 써도 된다. 번호만 쓰면 안 되는 이유가 있다. 노션 화면에서 번호는 속성 맨 끝에 작게 붙고, 보기마다 걸러지는 카드가 달라 번호만으로는 찾기 어렵다.

```markdown
## {이름}님 역할 ({프로젝트})
{역할 한 줄} — 근거 [기록 제목](링크), {잠정/확정}. 배정 업무 {n}건·이슈 {n}건, 기록 최근 갱신 {날짜}.

## 오늘({날짜}·{요일}) 할 일
1. **{번호} {카드 제목}** ({우선순위}, 기한 {날짜}) — ...

## {다음 외부 일정} 당일·직후
...

## 이번 주({다가오는 마일스톤·기한})
...

## 백로그
- 지금 가능: ...
- 대기: ... ({무엇} 수령·승인 후)

**권장: {가장 먼저 할 한두 가지}**

확인 경계: {읽기만 한 출처}, {실행하지 않은 것}, {확인하지 못한 것}.
```

보고를 마친 뒤 이어서 할 수 있는 일을 한 줄로 제안한다. 예: 업무 갱신 문구 초안 작성, 질문지 초안 작성. 사용자가 고르기 전에는 실행하지 않는다.

카드 수정 초안을 만들 때는 카드마다 `칸 | 현재 | 제안` 표로 보여 준다. 바꾸지 않는 칸은 표에서 뺀다. 사용자가 확인하면 그때 수정한다. 수정 직전에는 카드를 다시 읽는다. 초안을 만든 뒤 다른 사람이 고친 내용이 있으면 덮어쓰지 않고 먼저 알린다.
